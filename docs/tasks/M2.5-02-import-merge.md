# M2.5-02 — Import & Merge by UUID

**Milestone:** M2.5 — Portability
**Depends on:** M2.5-01
**Blocks:** M2.5-03
**Requirements:** §10.1, §10.2, §10.6
**Branch:** `feat/import-merge`

## Goal

Import that merges by UUID — idempotent, bidirectional, non-destructive — with deterministic
resolution for the four mutable fields that are not append-only.

## Why this is the hardest task in M2.5

Everything else in this milestone is plumbing. This is where correctness lives, and §10.6
specifies the exact properties that must hold.

## In scope

- Union-by-UUID merge across all five record types.
- Refusal of an unrecognized `schemaVersion` with a clear message, applying nothing (§10.2).
- The §10.1 conflict rules, verbatim:

| Field | Rule |
|---|---|
| `TaskItem.status` | **Derive** from the newest `statusChanged` event across both sets |
| `Project.lastStandupAt` | Take the **later** timestamp |
| `TaskItem.title`, `Project.name` | Later `modifiedAt` wins |
| `SourceRef.lastFetchedAt`, `.cachedSummary` | Later `lastFetchedAt` wins; `nil` loses to any value |

- Single-transaction application: a malformed file leaves the store untouched.

## Out of scope

- Preview UI and Replace mode — M2.5-03.
- CLI — M2.5-04.

## Acceptance criteria

All of §10.6's properties, as tests:

- [ ] **Idempotent** — importing the same file twice changes nothing on the second run.
- [ ] **Commutative** — merging divergent stores A→B and B→A converges to identical state.
- [ ] **Non-destructive** — a merge never deletes a task the import file lacks.
- [ ] Export → import into an empty store → object graph is identical.
- [ ] Malformed and truncated files are cleanly rejected, store unchanged.
- [ ] An unknown `schemaVersion` is refused with a clear message, not partially applied.
- [ ] `TaskItem.status` is derived from events, not copied from the field. Tested with a store
      whose cached `status` disagrees with its newest `statusChanged` event.
- [ ] Importing an **older** export after a newer one loses nothing.

## Notes for the spec/plan phase

- **Deriving `status` from the log is what makes the whole scheme robust** (§10.1). The stored
  field is a cache; the event log is the truth. Any mutable field that can be recomputed from
  the log, should be. This is also why M1-05 must never skip its `statusChanged` event — a
  transition without one silently reverts here.
- `lastStandupAt` takes the later value because "reporting is a historical fact. Taking the
  earlier one would re-report work already spoken aloud" (§10.1).
- The append-only design makes this nearly free: an event either exists on the target machine
  or it does not. There is no such thing as a changed event to reconcile. If the implementation
  starts needing event-level conflict logic, something upstream has gone wrong.
- The user must not have to remember which machine is authoritative (§10.1). Commutativity is a
  usability requirement, not a mathematical nicety.
