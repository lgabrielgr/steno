# M2.5-04 — CLI Export/Import Subcommands: design

**Date:** 2026-09-17 · **Task:** [`M2.5-04`](../../tasks/M2.5-04-cli-subcommands.md) ·
**Requirements:** §10.5, §10.6, §9.2 · **Branch:** `feat/cli-export-import`

## What this builds

`steno export` and `steno import` as subcommands on the app binary, plus `make export FILE=…`
and `make import FILE=…` wrapping them. Running a subcommand opens no window and needs no GUI
session; every target exits non-zero on failure, per §9.2.

M2.5-01 through M2.5-03 built the whole engine. `ExportEncoder.encode()` produces §10.2's
bytes, `ImportService.plan(_:mode:)` and `apply(_:backupWith:backupTo:)` perform §10.1's merge
in one transaction, `ImportPreviewSummary` renders §10.4's text, and `BackupWriter` writes
Replace's mandatory pre-wipe backup. **This task is a second surface over those types and adds
no export or import semantics of its own.** A behaviour that differs between the CLI and the
File menu is a defect in this PR, not a feature of it.

The testability is the real prize. §10.6's round-trip properties have so far been verified at
the unit level against types; a CLI that runs headless lets them be verified end to end,
through the same entry point a person would use.

## What this task decides

Five things the requirement leaves open. Each gets a `DECISIONS.md` entry.

| Question | Decision |
|---|---|
| How the binary tells a CLI invocation from a launch | `argv[1]` exists and does not begin with `-` |
| Where the CLI reads its store | `STENO_STORE_PATH` if set, else `StenoStore.defaultURL` — **CLI path only** |
| What happens when the app is already running | `import` refuses; `export` proceeds |
| What `--output` does to an existing file | Overwrites it, atomically |
| What `make import` exposes | Merge only — `--replace` stays on the binary |

## Architecture

### The entry shim, and the argv rule

`StenoApp` loses `@main`. A new `Steno/App/StenoMain.swift` takes it:

```swift
@main
enum StenoMain {
    static func main() {
        let arguments = CommandLine.arguments
        if CLIEntry.isCommandLineInvocation(arguments) {
            // main() runs on the main thread, which is what makes this legal.
            exit(MainActor.assumeIsolated { CLIEntry.run(arguments) })
        }
        StenoApp.main()
    }
}
```

That is the whole of the app target's share, and the brevity is the point: the shim is the one
piece the headless bundle cannot reach, so everything that could be wrong about it lives in
`StenoKit` instead. Note that it is `if` / `exit`, not `guard` / `else` — `App.main()` is
declared to return `Void` rather than `Never`, so a `guard` whose `else` branch called it would
not compile.

**CLI mode iff `CommandLine.arguments.count > 1` and `arguments[1]` does not begin with `-`.**
This is what makes the task file's "a double-click never lands in CLI mode" true by
construction rather than by hope: LaunchServices passes only dash-prefixed arguments — the
legacy `-psn_0_…` process serial number, and `-NSDocumentRevisionsDebugMode YES` when Xcode
launches the app — so no launch path that isn't a terminal can produce a bare first word.
`open -a Steno --args export` can, and that is a deliberate act.

The rule also decides what a typo does. `steno exprot` has a bare first word, so it is a CLI
invocation with an unrecognised subcommand: usage on stderr, exit 2. Falling through to the GUI
there would be the worse failure — a scripted export that silently launches a window and hangs
the script on a run loop that never returns.

Rejected alternatives. **A separate `steno` executable target** contradicts §10.5's
"subcommands on the app binary", doubles the signing configuration §9.3 pins, and gives the
user a second artifact to keep in sync. **Branching inside `StenoApp.init`** does not work at
all: SwiftUI's generated `main` starts `NSApplication` before any of our code runs, which fails
the acceptance criterion outright.

`main()` runs on the main thread, so the `@MainActor` services are reached through
`MainActor.assumeIsolated`. The GUI path is otherwise untouched — including the
`print("Steno launched")` line in `StenoApp.init`, which must not appear in CLI output.

### `StenoKit/CLI/`

Everything but the shim lives in `StenoKit`, because the test bundle is unhosted and links the
framework, not the app target (D-010). Four types:

**`CLICommand`** — a pure value, `Equatable` so parser tests assert on the case rather than on
behaviour:

```swift
public enum CLICommand: Equatable, Sendable {
    case export(output: URL?, includesCachedExternalData: Bool)
    case importFile(URL, mode: ImportMode)
}
```

It reuses `ImportMode` rather than declaring a second two-case enum, so `--replace` and the File
menu's Replace item are the same value flowing into the same `plan(_:mode:)`.

**`CLIParser`** — `static func parse(_ arguments: [String]) throws -> CLICommand`, throwing a
usage error carrying the text to print. It is reached only for an invocation
`isCommandLineInvocation` has already accepted, so the "is this the GUI?" question is asked in
exactly one place and the parser has one job. Hand-written, no argument-parsing dependency: the
surface is two subcommands and three flags, and §9.1's toolchain list is deliberately short.

**`CLIRunner`** — `@MainActor`, the only type that touches the store:

```swift
@MainActor
public struct CLIRunner {
    public init(
        container: ModelContainer,
        now: @escaping () -> Date = Date.init,
        exportedBy: String = ExportDocument.userAgent(),
        isAnotherInstanceRunning: @escaping () -> Bool = CLIRunner.anotherInstanceIsRunning,
        out: @escaping (String) -> Void = CLIRunner.writeOut,
        err: @escaping (String) -> Void = CLIRunner.writeErr)

    public func run(_ command: CLICommand) -> Int32
}
```

`run` returns an exit code and never throws: an error escaping into `main()` would terminate
with a backtrace where §9.2 asks for a message on stderr and a non-zero status.

**`CLIEntry`** — the seam between the two, and the only thing the shim names. Two statics:
`isCommandLineInvocation(_:) -> Bool` holds the argv rule, and `run(_ arguments:) -> Int32`
parses, resolves the store, builds a `CLIRunner`, and maps every outcome to an exit code. Store
resolution lives here rather than in `CLIRunner` so the runner takes a container and the tests
never touch an environment variable; a store that cannot be opened is exit 1 with the path in
the message, the same information `StoreFailureView` puts on screen.

`now` and `exportedBy` are injected for the reason every portability type already injects them
— `exportedAt` has to be assertable, and `Bundle.main` in the unhosted test bundle is the xctest
runner (D-010), so a defaulted user agent would put the runner's version into a file a test then
asserts on and pass anyway.

### Exit codes

`0` success · `1` the operation failed · `2` the command line was wrong.

Three codes, not a taxonomy. A script needs to know whether to retry, whether to alert, and
whether it invoked the tool wrongly; `ImportError.message` on stderr carries the detail, and a
numbered code per error case would be a second description of the same failure, free to drift
from the first.

### The store, and the one seam

The CLI resolves `STENO_STORE_PATH` when set, otherwise `StenoStore.defaultURL`. **The GUI path
ignores it entirely** — a stray environment variable inherited from a shell must never redirect
the real app's store.

This exists because the subprocess test below runs the real binary, and a test that opens
`~/Library/Application Support/Steno` is not a test anyone can run twice. It is honest to admit
it is a test seam; it is also the flag-free way to do it, which is why it is an environment
variable and not the `--store` option the task file's "keep the flag surface small" would have
counted against.

### The running-instance guard

`steno import` refuses when another Steno instance is running, before it reads the file:

> Steno is running. Quit it first — nothing was imported.

The hazard is specific. There is no cross-process change notification here, so a CLI import
writing to the store behind an open app leaves the GUI holding live SwiftData objects from
before the merge, and the next save in the GUI writes that stale state back over the imported
rows. `.stenoDidWrite` is a `NotificationCenter` post within one process (D-019) and does not
cross the boundary. Export is read-only and carries no such hazard, so it runs whether or not
the app is open — which matters, because M2.5-05 will auto-export from a machine where Steno is
by definition running.

Detection is `NSRunningApplication.runningApplications(withBundleIdentifier:)` filtered to
exclude our own `processIdentifier`. **This must be measured before it is relied on.** A
terminal-launched process inside an `.app` bundle that never creates `NSApplication` may or may
not register with LaunchServices, and if our own process registers, an unfiltered check would
refuse every import; if the *GUI* process somehow does not appear, the guard would silently
never fire, which is the failure mode this repo has already shipped once and written a memory
about. The plan phase verifies both directions with the app running and not running. If it
cannot be made to work, the guard is dropped and the hazard documented in the README — a guard
that cannot fire is worse than none, because it invites the reader to trust it.

The closure is injected, so both answers are testable without a second process.

## The two commands

### `steno export [--output PATH] [--include-cached]`

1. **Resolve the destination.** No `--output` → `ExportFilename.forDate(now())` in the current
   working directory. `--output` naming an existing directory → that same filename inside it.
   Otherwise `--output` is the file path, verbatim. A missing parent directory is an error, not
   an invitation to create one.
2. **Encode** through `ExportEncoder(context:includesCachedExternalData:now:exportedBy:)`.
   `--include-cached` sets §10.2's `includesCachedExternalData`, the same flag the save panel's
   checkbox sets.
3. **Write** with `.atomic`, overwriting.
4. Print the resolved path to stdout; exit 0.

`ExportFilename`'s own doc comment defers collisions to this task, and the answer is overwrite.
A scripted daily export to the same folder has to be re-runnable, and the same day's file must
be replaced rather than accumulating — a property M2.5-05's retention will depend on. Nothing is
lost that the store does not still hold: export is a pure read, and D-085 records the absence of
a write path on `ExportEncoder` as the design. The exposure is a mistyped `--output` clobbering
an unrelated file, accepted as the price of conventional `-o` behaviour.

### `steno import --file PATH [--replace]`

1. **Refuse if another instance is running.** Before the file is read, so a refused import has
   touched nothing at all.
2. **Read the file.** A read failure is exit 1 with the filename in the message.
3. **`plan(data, mode:)`.** An `ImportError` prints `.message` to stderr and exits 1. That is
   the same sentence the GUI banner shows, which is why `message` lives on the error and not in
   a view.
4. **Print the preview** — `ImportPreviewSummary.headline`, `.provenance`, `.lines` — to
   stdout. D-108 put that renderer in `StenoKit` for exactly this call site; a second renderer
   here would be two descriptions of one plan.
5. **An empty plan** prints "Nothing to import." and exits 0. That is §10.6's idempotency made
   visible: the second import of a file reports no work and, per `apply`'s own guard, posts
   nothing and writes nothing.
6. **Apply.** For `.replace`, build a `BackupWriter`, take `plannedURL()`, and pass both to
   `apply(_:backupWith:backupTo:)` — which writes the backup itself after its staleness check
   (D-110). Print the backup path on success. A `BackupWriter` that cannot be built is a
   refusal, not a warning: §10.1 makes the backup mandatory and `apply` refuses a `.replace`
   plan without a writer regardless, so the CLI cannot skip it even by accident.
7. Print a confirmation naming the file — and, for `.replace`, where the backup went; exit 0.

**No interactive confirmation.** The task file puts prompts out of scope, and `--replace` typed
on a command line is itself the explicit gesture §10.1 asks for — the GUI's typed confirmation
exists because a menu item is one click away from a mistake, which a flag is not.

## Output and error handling

Human-readable text on stdout, failures on stderr, `ImportError.message` verbatim. Nothing
machine-parses stdout: a script that needs the export path passes `--output` and already knows
it, so there is no reason to constrain the wording of a line a person reads.

Every failure message says what did not happen, matching the wording the GUI already uses —
"Nothing was imported", "nothing on this Mac was changed". The two failures the GUI learned to
distinguish in #30 stay distinct here: a store that cannot be *read* and a file that cannot be
*written* are different sentences, because they send the user to different places.

## Make targets

```make
export: build ## Export the store to FILE (FILE optional)
import: build ## Merge an export FILE into the store
```

Both depend on `build`, so they cannot run a stale binary. `make import` with no `FILE` exits 2
with a usage line rather than a `bash: unbound variable` trace — the Makefile's `SHELL` carries
`-u` (load-bearing, per its own comment) and an unset Make variable expands empty, so the check
is explicit. Both are added to `.PHONY`; both carry a `## ` marker so `make help` lists them.

**Replace is deliberately not reachable from a make target.** §10.1 says Replace must never be
the path of least resistance, and `make import FILE=x REPLACE=1` is the easiest thing in this
repo to typo into a wiped store. `steno import --file x --replace` is the only CLI route.

§10.5 writes `make export FILE=...`, but `FILE` is naturally optional for export — the filename
is derived from the date. The target accepts `FILE` without requiring it. Flagged in the PR body
rather than amended, since the requirement's intent is satisfied.

## Testing

Runner tests in-process, one smoke test through the real binary.

**The argv rule** — `isCommandLineInvocation` answers false for a bare argv, for
`-psn_0_123`, and for `-NSDocumentRevisionsDebugMode YES`; true for `export`, `import`, and
`exprot`. These four cases *are* the double-click acceptance criterion, stated as a property of
a pure function rather than as a claim about LaunchServices that nobody can run.

**Parser** — every flag and its absence; `--file` missing; an unknown flag; `export` with a
trailing positional argument; `exprot` → usage error with a non-empty message.

**Runner**, against a temp-file container (`StenoStore.live(at:)`, held for the test's lifetime
— `mainContext` does not retain its container, and tests build their own `ModelContext`):

- Export bytes are **byte-identical** to `ExportEncoder(...).encode()` over the same store with
  the same injected `now` and `exportedBy`. That is the acceptance criterion "identical to what
  the GUI produces", stated as equality against the type the GUI calls rather than as a
  structural comparison that could pass over two different files.
- Export → import into a second empty store → object graph identical. §10.6, end to end.
- Import the same file twice → the second run prints nothing to import, exits 0, and leaves the
  store byte-identical on re-export.
- A malformed and a truncated file → exit 1, `ImportError.message` on stderr, store unchanged.
- `--output` at an existing directory lands the dated filename inside it; `--output` at an
  existing file overwrites it.
- The instance guard, injected true → exit 1, and the input file is never read. Injected false
  → the import proceeds. Both directions, so the guard is falsifiable.
- `--replace` writes a backup that is itself a valid export of the pre-replace store, and the
  resulting store matches the file.
- An unwritable output path → exit 1 with a message naming the path.

**One subprocess test** locates `Steno.app/Contents/MacOS/Steno` beside the test bundle in
DerivedData, runs `export --output <temp>` with `STENO_STORE_PATH` pointed at a temp store, and
asserts exit 0 and a decodable `ExportDocument`. The scheme already builds the app for testing,
so the binary is there; **if it is missing the test fails rather than skipping**, because a
skipped test is a test that cannot fail. The sandbox profile is `(allow default)` minus
networking, so spawning is permitted. What this proves is that the real binary runs a subcommand
to completion and exits, rather than entering a run loop — which is the observable form of "does
not open a window or require a GUI session".

Mutation-check the new assertions before the PR: invert the guard, drop the `.atomic` overwrite,
and return a stale plan, and confirm the suite goes red for each.

## Manual verification (PR body)

Agents cannot see a window, so the following are run by hand and recorded:

- `make export` and `make export FILE=/tmp/x.json`, then `make import FILE=/tmp/x.json`.
- A double-click on `Steno.app` opens the window and does not enter CLI mode.
- `steno import` with the app open is refused; with the app quit, it succeeds.
- `steno export` runs with the app open and produces a valid file.

## Known limitation carried forward

The File menu's Export/Import/Replace items gate on `@FocusedValue`, so they are disabled when
the main window is closed — shipped knowingly with #30. The decision taken for this task is to
**narrow the claim**: document the limitation, keep `reveal()` for the minimized and
other-Space cases, which do work, and leave the lift-to-`StenoApp` change unbuilt. The CLI
landing in this PR gives the closed-window case a working path, which is part of why narrowing
is acceptable. Recorded in `DECISIONS.md` so a later reader does not find the gate and assume it
is a bug nobody noticed.

## Out of scope

- **New export or import semantics.** This is a surface over M2.5-01 and M2.5-02 (task file).
- **Interactive prompts**, including a typed confirmation for `--replace` (task file).
- **Auto-export** — M2.5-05, which consumes this task's destination resolution.
- **The closed-window menu fix** — narrowed above, not built.
- **A `--store` flag.** The environment variable is a test seam and is documented as one; it is
  not a supported way to run Steno against an alternate store.
