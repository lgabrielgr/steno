# M2.5-01 — Export Encoder: design

**Task:** [`docs/tasks/M2.5-01-export-encoder.md`](../../tasks/M2.5-01-export-encoder.md)
**Requirements:** §10.2 (format), §10.3 (secrets), §10.6 (test requirements), §8, §3 (field tables)
**Branch:** `feat/export-encoder`
**Date:** 2026-09-11

The first half of the only mechanism by which Steno will ever move between machines (§10, D1).
Sync is cancelled, so there is no second copy: a field this encoder quietly drops is user data
that no later task can recover. That single fact decides most of what follows — the field
allowlist test, the total ordering, and the refusal to filter anything.

This PR produces `Data` and a filename. It writes no file, opens no panel, and decodes nothing
against the store. Import is M2.5-02; disk I/O is M2.5-03 and M2.5-04.

---

| `TaskItem.status` is a cache; the newest `statusChanged` event is the truth | §10.1, ARCHITECTURE §1 | Export still carries the field — it is a field of the record — but M2.5-02 derives rather than copies it. Nothing here computes status |

## 2. `ExportEncoder`: a reader, not a service

New directory `StenoKit/Portability/`, which ARCHITECTURE §5 already reserves for M2.5. The
encoder sits with persistence, below the view-model layer. Nothing in `Steno/` changes.

```swift
@MainActor
public struct ExportEncoder {
    public init(
        context: ModelContext,
        includesCachedExternalData: Bool = false,
        now: @escaping () -> Date = Date.init,
        exportedBy: String = ExportDocument.userAgent()
    )

    public func snapshot() throws -> ExportDocument
    public func encode() throws -> Data
}
```

`@MainActor` because `ModelContext` is not `Sendable`, and `now` injected so `exportedAt` is
assertable — both for the reasons `ReportGatherer` and `StandupService` already record.

**Named `Encoder`, not `Service`, for `ReportGatherer`'s reason.** `CaptureService`,
`StatusService` and `NoteService` share a shape: inject `save`, mutate, post `.stenoDidWrite`.
This type does none of those. A name ending in `Service` is an invitation to add the `save`
parameter its siblings have, by symmetry, and a write on the export path is a bug with no
symptom until a merge disagrees months later.

**`snapshot()` and `encode()` are separate because the tests need different things.** Ordering,
field selection, and value mapping are properties of a typed value and are asserted on
`ExportDocument`. Key order and the absence of credential patterns are properties of *bytes* and
have to be asserted on `Data`. Collapsing the two would force half the suite to parse JSON to
ask questions the type already answers, and the other half to assert on a type that cannot
answer them at all.

### Rejected: making the `@Model` classes `Codable`

Least code, worst format. SwiftData's `@Model` macro and `Codable` synthesis conflict; the
`task` relationship is a cycle that needs manual exclusion; and the wire format would become
whatever the persistence layer happens to hold at the time. §10.2's format is a compatibility
contract that M2.5-02 reads and that outlives any given schema — it needs its own declaration.

### Rejected: write-only `Encodable` DTOs, with M2.5-02 declaring a decodable mirror

A smaller PR, and two declarations of one wire format. They drift, and the drift is silent: an
encoder that gains a field and a decoder that does not is precisely the "export quietly drops a
field" failure the task file names, arriving by a different door. The DTOs are `Codable` in both
directions and M2.5-02 decodes these exact types. The `schemaVersion` refusal (§10.2) stays with
M2.5-02, which is where reading happens.

## 3. The envelope, and why `.sortedKeys` is mandatory

```swift
public struct ExportDocument: Codable, Equatable, Sendable {
    public static let currentSchemaVersion = 1

    public let schemaVersion: Int
    public let exportedAt: Date
    public let exportedBy: String
    public let includesCachedExternalData: Bool
    public let projects: [ExportedProject]
    public let tasks: [ExportedTask]
    public let events: [ExportedEvent]
    public let sourceRefs: [ExportedSourceRef]
    public let reports: [ExportedReport]
}
```

**`.sortedKeys` is required, and this was measured rather than reasoned about.** The appealing
alternative — rely on synthesized `Codable` emitting keys in property declaration order, which
would match §10.2's envelope exactly — is simply false. `Codable` synthesis writes into a
dictionary, so without the option the key order is the dictionary's hash order, and that order
**differs between processes**. Two runs of the suite produced:

```
includesCachedExternalData, exportedBy, events, sourceRefs, schemaVersion, reports, exportedAt, tasks, projects
sourceRefs, events, exportedAt, schemaVersion, reports, tasks, includesCachedExternalData, exportedBy, projects
```

Two exports of an unchanged store would be byte-different files. That defeats the diffability
§10.2 asks for by name and turns M2.5-05's auto-export history into churn — and no single test
run can see it, which is what makes it worth stating here.

So the file is alphabetical, `schemaVersion` is not first, and §10.2's example ordering is
illustrative only. JSON objects are unordered by definition, so nothing that reads the file is
affected; only a human skimming it is, and alphabetical is at least predictable. A test still
pins the literal ordered key sequence, now against the sorted order.

Formatting is therefore:

| Option | Set | Why |
|---|---|---|
| `.prettyPrinted` | yes | §10.2's "human-readable, greppable, diffable" |
| `.sortedKeys` | yes | The only thing that makes the byte output deterministic at all |
| `.withoutEscapingSlashes` | yes | `SourceRef.url` otherwise exports as `https:\/\/…`, which defeats grepping for a link |

`exportedBy` is `"steno/<CFBundleShortVersionString> (macOS)"`, matching §10.2's example, with
`ExportDocument.userAgent()` reading `Bundle.main` and falling back to `steno/unknown (macOS)`.
**It must be injectable, not read inline.** The test bundle is unhosted (D-010), so `Bundle.main`
there is the xctest runner: a non-injected version string would put the runner's version in every
envelope the tests assert on, and the assertion would pass anyway.

## 4. The record DTOs

Five flat structs in `ExportRecords.swift`, mirroring the §3 field tables one-for-one. Names are
`ExportedProject`, `ExportedTask`, `ExportedEvent`, `ExportedSourceRef`, `ExportedReport` — the
`Task` shadowing problem (§3.2) does not reach `ExportedTask`, and §10.2's key stays `"tasks"`.

What is deliberately **not** carried:

| Omitted | Why |
|---|---|
| `TaskItem.sourceRefs` | §3.4 makes `SourceRef.taskID` authoritative and gives refs their own top-level array. Carrying both would let a file disagree with itself, and M2.5-02 would have to pick a winner |
| `SourceRef.task` | The same fact as `taskID`, as a relationship. Serializing it is a cycle |
| Anything from `AppSettings` | O-9, decided in §8 below |
| `SourceRef.cachedSummary`, `.lastFetchedAt` | Only when `includesCachedExternalData` is false. §7 |

**Nothing is filtered.** Archived projects, archived tasks, redacted events and undone reports
all export, carrying their flags. The tempting filter — "redacted events are hidden from
summaries, so why export them?" — is the worst bug available in this file: exported into an empty
store, a dropped redacted event does not lose its *visibility*, it loses its *row*, and §3.3's
append-only log is the thing every summary is derived from. `isRedacted` and `isUndone` are also
exactly the two flags O-8 leaves open for M2.5-02; a merge cannot resolve a flag it never
received.

`Event.payload: Data?` encodes as base64, which is neither greppable nor diffable — and that is
**already true of ordinary stores**, not a future concern. `StandupService` writes a
`StandupReportedPayload` on every Copy (D-085), so every `standupReported` event in a real export
carries an opaque `eyJyZXBvcnRJRCI6…` where the report id would otherwise be greppable.

Base64 stays anyway, and the reason is round-trip fidelity rather than convenience. `payload` is
`Data`, and §10's first criterion is that every field survives byte-exactly. Embedding it as
nested JSON means re-serializing on import, which does not reproduce the original bytes — key
order and whitespace are not preserved — so the field chosen for readability would become the one
field that does not survive the trip. §10.2 states the trade instead (D-097).

## 5. Timestamps: milliseconds, and what "round-trip fidelity" can mean

§10.2's example shows `"2026-08-10T14:22:05Z"`. Whole seconds truncate, and the truncation is not
cosmetic: §10.1 resolves three of its four merge rules by comparing timestamps, so two notes typed
in the same second become a tie that no rule can break, and their order in the log is
unrecoverable. Export is written at millisecond precision:

```
"timestamp": "2026-08-10T09:14:02.481Z"
```

`dateEncodingStrategy` is `.custom`, formatting through
`Date.ISO8601FormatStyle(includingFractionalSeconds: true)`. The decode side is `.custom` too and
tries that style first, then a plain `Date.ISO8601FormatStyle()` — a person hand-editing a file
(which is half of why §10.2 chose JSON) should not produce one the app rejects. M2.5-02 inherits
that leniency, and reads these two styles rather than re-deriving the format.

A `FormatStyle` rather than an `ISO8601DateFormatter`: the formatter is a non-`Sendable` class, so
a shared instance is not expressible as a `static let` under Swift 6's concurrency checking, and a
per-call instance is the allocation this path least wants.

**This changes what a round-trip can assert, and the measured behaviour is narrower than it
looks.** `Date` is a `Double` of seconds, and **formatting truncates at the millisecond rather
than rounding**. At epoch 1.7e9 a decimal like `.481` is not representable: it is stored as
`.4809999…` and emitted as `.480`. Measured across a range of values:

| Fractional second | Emitted | Round-trips exactly |
|---|---|---|
| `.0`, `.125`, `.25`, `.5` | `.000`, `.125`, `.250`, `.500` | yes |
| `.1` | `.099` | no — short by 0.999 ms |
| `.481` | `.480` | no — short by 0.999 ms |
| `.4817263` (clock-shaped) | `.481` | no — short by 0.726 ms |

Two claims follow, tested differently:

- A date whose fractional second is an **eighth** — `0`, `.125`, `.25`, `.375`, `.5`, `.625`,
  `.75`, `.875` — round-trips *exactly*. These are the only values both exactly representable as
  a `Double` and exactly expressible in three decimals; "dyadic" alone is too broad, since
  `.0625` is dyadic and still truncates to `.062`. Every fixture date **used in a direct `==`
  assertion** is a whole second or an eighth, which is what lets `ExportDocument: Equatable` be
  compared with `==` in the encode→decode test instead of field-by-field with a tolerance. The
  ordering and tolerance tests deliberately use values that do not survive — `.5001`, `.5002`, a
  clock-shaped date — because that is the behaviour they exist to pin.
- Every other date, `Date.now` included, round-trips to **within 1 ms and never later** than the
  original. Asserted with an explicit tolerance and a direction, since truncation is one-sided.

Stating this now is cheaper than discovering it in M2.5-02, where an `==` on a clock `Date` would
fail for a reason that looks like a merge bug. That task's "object graph is identical" criterion
means identical at this precision.

**Spec amendment.** §10.2's example contradicts this, so the same PR amends the example to the
fractional form, bumps REQUIREMENTS.md to v1.16, and adds a changelog line in the established
"Found while implementing M2.5-01" form. Per CLAUDE.md this is an amendment, not a silent
deviation, and the PR body says so.

## 6. A total order, not merely a sort

Every array is sorted in memory after mapping, and every comparator ends in `id.uuidString` so no
two records can compare equal:

| Array | Sorted by | Why |
|---|---|---|
| `projects` | `sortOrder`, `name`, `id` | The order `MainWindowModel.fetchProjects` shows. `sortOrder` is not unique, and neither is `name` |
| `tasks` | `createdAt` **as emitted**, `id` | New tasks land at the end of the array |
| `events` | `timestamp` **as emitted**, `id` | The large array. Appends land at the end, so a day-over-day diff is additions only |
| `sourceRefs` | `taskID`, `kind`, `identifier`, `id` | §3.4's dedup key — the identity the model already defines — and it groups refs under their task. The `id` is still required: the dedup rule is enforced in code, not by a database constraint (§3.4), so two rows sharing a key are possible and the order must stay total |
| `reports` | `generatedAt` **as emitted**, `id` | Appends land at the end |

The UUID tie-break carries the actual weight. Without it, two events captured in the same
millisecond sort arbitrarily, two consecutive exports of an unchanged store differ, and M2.5-05's
auto-export history becomes noise rather than a backup log — which is the reason the task file
gives for wanting stable ordering in the first place.

**"As emitted" is load-bearing too, and the first implementation missed it.** The three date keys
are the ISO-8601 string the file carries, not the in-memory `Date`. Two events a fraction of a
millisecond apart are distinguishable in memory and identical on the wire, so ordering on the
`Date` puts them in a sequence the file cannot express — any store built from that file ties on
them, falls through to the id, and can reverse the pair relative to the export it came from. An
unchanged store would then export differently after a round trip. Keying on the emitted value
makes the order derivable from the file's own contents, which is what M2.5-02's convergence and
M2.5-05's history both need. Caught in review.

Sorting happens in memory rather than in `FetchDescriptor.sortBy` so the comparators live in one
place next to each other, and so `SourceRefKind` — an enum, which a SwiftData `#Predicate`
cannot express in either spelling (`EventQueries.swift`, D-085) — is not a special case. D18 caps the live
dataset under 20 tasks; events accumulate over years but a whole-store fetch at this scale is
unremarkable. Export is not on the capture path, so §1.1's latency rule is not in play; M2.5-05's
"export on quit must not delay quit" is that task's criterion and is noted for it.

## 7. Cached external data

`includesCachedExternalData` is an input to the encoder and a field of the envelope. When it is
false — the default (§10.2) — `cachedSummary` and `lastFetchedAt` are not carried. The mechanism
is synthesized `Codable`'s use of `encodeIfPresent` for optional properties: a `nil` omits its
key rather than writing `null`. The same mechanism omits `completedAt`, `modelUsed`,
`staleThresholdDays`, `url`, `payload` and `lastStandupAt` when those are genuinely absent, which
keeps the file readable.

The `sourceRefs` array itself is always present, with every other field of every ref. §10.2 is
explicit that only the two fields are omitted, and the reason matters: a ref the user attached by
hand, or one whose source text was later redacted, exists nowhere else and cannot be re-derived by
re-running extraction on the target machine.

This interacts with the allowlist test, and the interaction is a trap — see §12.

## 8. The two open questions this task owns

**O-9 — are `AppSettings` exported? No.** The hotkey chord and FR-6's default project are
machine-local configuration, not domain data. Three reasons, in the order they matter: the
default project is a `UUID` that may name a project the target machine does not have, so
importing it installs a dangling pointer into a capture path FR-1.4 requires never to block; a
chord that is free on machine A may collide with another app's on machine B, and §10's import has
no way to ask; and M2.5-02's merge would need a rule for a record type that is not a record.
`AppSettings.swift`'s doc comment already asserts this outcome — this decision is what makes the
assertion true rather than aspirational, and D-056 is updated to point at it.

**O-7 — is integration configuration exported here? No — deferred to M4-04 and M5-02.** There is
no `SourceConnector`, no Jira site URL and no MCP server definition in the codebase to serialize;
`StenoKit/Sources/` does not exist. Designing their export now means inventing the shape of
records that do not exist, in the one file format that has to stay compatible. §10.3 permits this
configuration to be exported "with the target machine prompting for credentials on first use" —
that permission stands, and the task that creates the records adds them under a bumped
`schemaVersion` with the credential-prompt path it needs anyway. Both moves are recorded in
`DECISIONS.md` and named in the PR body, as the task file requires.

## 9. Secrets: what the tests can and cannot prove

§10.3 is candid that the guarantee is structural — secrets live in Keychain (§8), the encoder
serializes SwiftData, so no credential can be present — and equally candid that the structural
argument is not enough, "because construction-based guarantees erode silently when someone later
adds a field."

A single scan-the-output test does not catch that erosion. It passes on an empty store; it passes
on a store full of ordinary notes; it would pass on a store holding a field named `apiToken`
whose value matched no vendor's prefix. So there are several, failing for different reasons:

1. **Pattern scan, with a positive control.** `CredentialPatterns` is a pure scanner over a
   string. The negative direction runs it over the real exported bytes of a realistic fixture. The
   positive direction feeds it a synthetic export containing each marker in `CredentialPatterns.all`
   in turn — `sk-ant-`, `sk-proj-`, `ATATT`, `ghp_`, `xoxb-`, `xoxp-`, `AKIA`, `Bearer …` — and
   requires each to be flagged **by name**, not merely that something matched. **The positive
   control is the test.** Without it the negative direction is unfalsifiable — it cannot distinguish "no
   secrets present" from "the scanner matches nothing, ever".
2. **Key allowlist**, in §12 — and it takes *three* assertions, not one, each catching what the
   others cannot.
   - *From the JSON:* catches a field that reaches the file and should not.
   - *From the record types:* reading the emitted JSON does **not** catch the case §10.3 is
     actually about — a new optional field is `nil`, `encodeIfPresent` omits its key, and the
     JSON is byte-for-byte unchanged. A field with no fixture value is never anything but `nil`,
     so it stays invisible forever. Mutation-tested during design: `let apiToken: String?` sailed
     through the JSON assertion untouched. `Mirror` over each record's stored properties fails
     the moment the field is declared, valued or not.
   - *From the models:* both of the above compare the *records* to a literal set, so a field
     added to `Project` and forgotten in `ExportedProject` changes nothing — no DTO growth, no
     JSON change, and the export silently drops user data. Added in review. `Mirror` over each
     `@Model`, against the same set plus a named exclusion list.

   One level above all three, a gate derived from `StenoStore.models()`, so a sixth model added
   to the schema with no DTO fails rather than being exported by nothing.

`CredentialPatterns` lives in `StenoTests/Portability/`, not in `StenoKit`. Nothing in production
reads it: §10.3 asks for an assertion about the output, not a runtime guard, and a scanner shipped
in the framework with no caller is an invitation to wire it into the write path, where it would
become a filter on user content. M2.5-05's tests, which assert the same property on the unattended
auto-export path, link it from the test bundle.

**An explicit non-goal: user-typed content is never sanitized.** If the user pastes a token into a
note, the export contains it, and that is correct. §10.3 governs credentials *the app holds*.
Stripping content from a note because it pattern-matches would be the export silently deleting the
user's data — with, once again, no second copy. The realistic fixture is built through
`CaptureService`, `StatusService` and `NoteService` rather than by hand, so it holds what the
store actually holds and no fixture-shaped secret is smuggled in.

## 10. The filename

`ExportFilename.forDate(_:)` returns `steno-export-2026-08-11.json`, formatted through a
`Date.ISO8601FormatStyle` reduced to its year/month/day components, with the time zone injectable
and defaulting to `.current`. An ISO-8601 style rather than a `DateFormatter` with a format
string: ISO-8601 is Gregorian and locale-independent by definition, so there is no locale to pin
and no user calendar left to produce a different year.

**The date is local, not UTC.** A user who exports at 20:00 on the 11th in PDT should get the
11th in the filename, not the 12th; the name exists so a human can find the file, and a name that
disagrees with the day they remember is worse than no date at all. `exportedAt` inside the file
remains UTC, which is where precision and comparability matter. The test pins this with an
injected time zone at an instant where the two dates differ — without that, the test passes in
any time zone for the wrong reason.

Collisions (two exports on one day, or an existing file at the path) belong to whoever writes
bytes: M2.5-03's save panel, M2.5-04's `--output`, and M2.5-05's retention policy.

## 11. Error handling

`throws`, from exactly two places: `context.fetch` and `JSONEncoder.encode`.

**No `ExportError` type.** An encoder over a struct with no cycles and only JSON-safe types has
no failure case anyone can construct, and an error enum whose cases are unreachable is noise that
invites `try?` at the call site. M2.5-02 has real failures to name — unknown `schemaVersion`,
malformed file, truncated file — and should own that type.

Three properties, each tested:

- **An empty store is not an error.** It exports a valid document with five empty arrays. This is
  not a corner case: M2.5-05 auto-exports on quit and defaults ON, so the first export on a new
  machine is very likely the empty one, and it must decode cleanly rather than produce a file
  M2.5-02 later rejects.
- **Partial output is impossible.** The encoder returns `Data` or throws. It never touches the
  filesystem, so the half-written-file failure cannot occur here; it belongs to M2.5-03/-04.
- **No `try?` on this path.** A swallowed fetch is a silently short export, which is data loss
  that looks like success.

Surfacing a failure to a person is out of scope — there is no UI in this PR.

## 12. Verification

`make build && make test && make lint` green before the PR (§9.5 step 4). Tests in
`StenoTests/Portability/`, grouped by what each can actually detect.

**Envelope**

- `schemaVersion` is present and equals 1.
- The injected `now` and `exportedBy` appear verbatim, and `userAgent(bundle:)` is asserted on
  both branches against real bundles — a fabricated one carrying a version, and the unhosted test
  bundle, which genuinely has none. Prefix-and-suffix assertions pass for an implementation that
  never reads the bundle.
- The literal ordered sequence of top-level keys is the **alphabetical** one `.sortedKeys`
  produces — not §10.2's example order, which v1.16 marks illustrative. Falsified by removing
  `.sortedKeys` and running the suite twice: the failures differ between runs, which is the
  nondeterminism the option exists to remove.
- An empty store yields five empty arrays and decodes back.

**Completeness — four guards, layered, because each is blind to what the next catches**

- *Key allowlist, from the JSON:* each record type's emitted key set equals a literal expected
  set. Catches a field that reaches the file and should not.
- *Key allowlist, from the record types:* `Mirror` over each record's stored properties equals the
  same set. Not redundant — mutation testing proved the JSON assertion alone misses a new optional
  field, which encodes to no key at all while it is `nil`. Both read one shared declaration of
  the allowed keys, so they cannot drift apart.
- *Key allowlist, from the models:* `Mirror` over each `@Model`'s stored properties equals that
  same set plus a named exclusion list. This is the direction the other two cannot see — a field
  added to a model and forgotten in its record. Added in review.
- *Model coverage:* the guarded model names are checked against `Schema(StenoStore.models())`, so
  a sixth model with no DTO fails here rather than being silently absent from every export.
- *Value mapping:* every field asserted individually after decoding. Neither key test sees
  `createdAt` written into `statusChangedAt` — both keys present, both plausible dates. Verified
  by swapping two mappings in the encoder and confirming it goes red.

Both run against a **maximal fixture in which every optional is non-nil** — `completedAt`,
`modelUsed`, `staleThresholdDays`, `url`, `payload`, `lastStandupAt`, and `cachedSummary` /
`lastFetchedAt` with the flag on. This is the trap §7 flags: `encodeIfPresent` omits a `nil` key,
so a fixture that leaves an optional unset makes the allowlist blind to exactly the field nobody
remembered — the failure it exists to catch. The maximal fixture is constructed directly via
`@testable` access; the realistic fixture of §9 is built through the production services. Both are
needed and they are not interchangeable.

**Ordering**

- Records inserted in an order that *disagrees* with the expected output order, then asserted
  against the expected order. Encoding twice and comparing the two results proves nothing.
- Tie-break: two events with identical timestamps, inserted into two stores in opposite orders,
  produce the same array.

**Dates**

- An eighth-of-a-second fraction is emitted exactly (`…20.500Z`).
- Two events 1 ms apart stay distinct and correctly ordered — the falsifiable form of §5's
  decision, since whole-second encoding collapses them and this goes red. Asserted as distinct
  and ordered, not as exact values: both truncate down by up to a millisecond.
- An eighth-of-a-second timestamp survives encode→decode exactly; a clock-shaped one lands within 1 ms and
  never later — one-sided, because encoding truncates rather than rounds.
- A real `standupReported` payload survives byte-exactly, compared against bytes captured before
  the round trip. Asserting only that it still parses would pass for an encoder that substituted
  a different valid payload.
- A hand-edited whole-second timestamp still decodes (§10.2's inspectability), and a string that
  is not a date at all is rejected as a `DecodingError` rather than defaulted.

**Cached external data**

- Default: `sourceRefs` present and non-empty; neither `cachedSummary` nor `lastFetchedAt` appears
  anywhere in the bytes; the envelope flag reads `false`.
- Opt-in: both fields present with correct values and the flag reads `true`.

**Not filtered**

- A store containing an archived project, an archived task, a redacted event and an undone report
  exports all four, with their flags intact.

**Secrets** — §9's two directions. The positive control is table-driven; `make test` does not print
parameterized cases (xcbeautify swallows them), so the plan confirms they ran rather than reading
silence as success.

**Filename** — a date whose month *and* day are single-digit (2023-01-05), because a two-digit
date cannot fail for padding and the first version of this test used one. Plus an injected time
zone at an instant where local and UTC dates differ, in both directions, which pins the
local-date decision.
