# M2.5-05 — Auto-Export: design

**Date:** 2026-09-18 · **Task:** [`M2.5-05`](../../tasks/M2.5-05-auto-export.md) ·
**Requirements:** §10.5, §10.3, FR-6, §8, §13 · **Branch:** `feat/auto-export`

## What this builds

Automatic, unattended export to a user-chosen folder, **on by default**, introduced by a
first-run sheet rather than buried in Settings. Two triggers — on quit and daily — write
§10.2's JSON to `~/Steno Backups` (or wherever the user points it), keep the folder bounded at
fourteen files, and make any failure impossible to miss.

M2.5-01 through M2.5-04 built everything this writes. `ExportEncoder.encode()` produces the
bytes, `ExportFilename.forDate` names the file, `BackupWriter` is the worked example of an
unattended write, and `CLIRunner+Export.resolveDestination` already anticipates this task by
name — "M2.5-05 points a folder at a sync drive and wants exactly this". **This task adds no
export semantics.** A file written by auto-export must match one `steno export --include-cached`
would produce from the same store, record for record — the envelope's `exportedAt` and
`exportedBy` differ by construction, and nothing else may. A difference elsewhere is a defect in
this PR.

What is new is the *unattended* part, and that is where the design weight sits. With sync
cancelled (D1, §14) and no remote copy anywhere, an auto-export that fails silently leaves the
user with no backup and no knowledge that they have no backup. §10.5 names that as the one
unacceptable behaviour, and half of what follows exists to make silence unreachable.

## What this task decides

Eight things §10.5 leaves open. Each gets a `DECISIONS.md` entry, D-120 through D-127.

| Question | Decision |
|---|---|
| Where a default-ON export writes before the user picks anything | `~/Steno Backups` — created on demand, deliberately **not** `~/Documents` |
| Which triggers ship, and their defaults | Both, both on; quit is unconditional, daily is ≥24h since last **success** |
| Whether auto-exports carry cached external data | Yes, for `BackupWriter`'s reason — this is the backup story |
| How a failure reaches the user | Persisted status with three readers; never a system notification |
| How the folder stays bounded | Keep 14 newest by the date **in the filename**; surplus to the Trash |
| What stops the folder being Steno's own store | `StoreFileGuard`, extracted from the CLI and shared |
| What "surfaced during onboarding" means here | One sheet, on the main window's existing sheet machinery |
| What else the new Data pane carries | Auto-export only; FR-6's cache purge waits for M4 |

## D-120 — Default ON means writing somewhere from the first launch, and that somewhere is `~/Steno Backups`

§10.5 says auto-export "should default to ON during onboarding rather than being an opt-in
setting", because "manual export's failure mode is human: forgetting to run it". A default-ON
setting with no folder configured would reproduce exactly that failure mode with extra steps —
it would be on, and it would do nothing, until a human acted.

So the folder has a default, the default exists from the first launch, and the onboarding sheet
is about *where*, not *whether*.

**`~/Steno Backups`, not `~/Documents/Steno Backups`.** `~/Documents`, `~/Desktop` and
`~/Downloads` are TCC-protected for every app, sandboxed or not — this app being deliberately
unsandboxed (`Steno.entitlements`) buys nothing here. The first write into one of them raises a
system prompt, and the trigger most likely to arrive first is `applicationWillTerminate`: a
permission dialog appearing as the user quits, attached to an app that is going away, is the
worst possible first contact with a feature whose entire promise is that it works without being
watched. The home directory itself is not TCC-protected, so the default path raises no prompt
at any time.

Pointing the folder at Dropbox, iCloud Drive or Google Drive — §10.5's recommendation, and the
reason this feature is the substitute for cancelled sync — goes through `NSOpenPanel`, and the
panel *is* the grant: choosing a folder is what gives an unsandboxed app durable access to it.
That satisfies the task's "sandbox/permission handling persists across relaunch" criterion by
using the mechanism macOS provides rather than by storing a security-scoped bookmark the
unsandboxed app has no use for. The stored value is the path.

Rejected: **auto-detecting a cloud drive** and defaulting into it. Steno would be writing the
user's work into a folder that syncs off the machine without anyone having said so. The
suggestion belongs in the sheet, where it is a sentence the user reads, not a guess the app
acts on.

Rejected: **on-but-unconfigured**, with a nag until a folder is chosen. It is the human failure
mode again, and it means the fresh install most in need of a backup is the one that has none.

## D-121 — Both triggers ship on; quit is unconditional, daily is measured from the last success

- **Quit** — `applicationWillTerminate` runs an export with no dueness check. Every quit
  rewrites that day's file with the freshest store, which costs one atomic write and buys the
  property that the backup is never older than the last time the user closed the app.
- **Daily** — `AutoExportDue.isDue` is consulted at launch and on an hourly tick: due when
  there has never been a successful export, when ≥24h have passed since the last one, or when
  the last success is *in the future* (a clock that moved backwards must not disable backups
  until it catches up).

The interval is measured from the last **success**, never from the last attempt. A folder that
has gone missing therefore retries on the next tick instead of going quiet for a day — the
failure stays live and keeps re-announcing itself, which is the behaviour a backup deserves.

**Force-quit loses nothing**, and the reason is worth stating plainly because the acceptance
criterion asks for it: an export is *derived* from the store. SwiftData has already persisted
the data; a missed quit-export means the file on disk is older than the store, not that
anything was lost. The daily trigger closes that gap, and the two triggers exist precisely
because each covers the other's blind spot — quit misses a `kill -9`, daily misses a machine
that quits before the day rolls over.

**Quit latency is measured, not asserted.** §13's rule is about capture, but the reasoning
carries: a quit that visibly hangs teaches the user to force-quit, which is the one path that
skips the export. The perf test measures `AutoExportService.run` itself rather than the
terminate handler around it, and gates the number rather than asserting it in prose — D-025 is
the standing example of a decision record carrying a performance claim that was asserted rather
than measured, and was wrong by an order of magnitude. It asserts the mean over repetitions
rather than the worst of ten, which is D-064's rule for exactly this kind of test on CI
runners.

Rejected: **a single "export when stale" trigger** with no user-facing choice. Fewer states,
but it gives up the ability to turn off the quit path alone if it ever proves annoying, and
that is the one of the two most likely to.

Rejected: **skipping the export when the store has not changed since the last one.** It saves a
write per quit in exchange for a new question — "has anything changed?" — whose wrong answer is
a silently stale backup. The write is cheap; the question is not worth introducing.

## D-122 — Auto-exports include cached external data

`includesCachedExternalData: true`, hard-coded, with no setting.

`BackupWriter` already documents the reasoning for the one other unattended write in the
product: a snapshot that silently drops `cachedSummary` and `lastFetchedAt` is not one anybody
can restore from, and §10.1's "nil loses to any value" would hand those fields away on the way
back in. §10.5 calls auto-export "the backup story as well as the transfer story", so it is the
same argument, unchanged.

§10.2 excludes cached data from an ordinary export because it is bulky and re-fetchable — which
is true of a file a person is about to email themselves, and beside the point for the file that
is the only copy of their store outside the store. Until M4 lands there is no cached data at
all, so the decision costs nothing today and is correct on the day it starts costing something.

Rejected: **a toggle in the Data pane**. One more setting and one more state combination to
test, for a question the user has no basis to answer before the integrations that populate
those fields exist.

## D-123 — A failure is persisted status with three readers, never a system notification

One `AutoExportStatus` value, JSON-encoded into a single `UserDefaults` key — the shape
`AppSettings.hotkeyChord` already uses, and one key rather than four so a success and a failure
record cannot disagree about which is current:

```swift
public struct AutoExportStatus: Codable, Equatable, Sendable {
    public struct Success: Codable, Equatable, Sendable {
        public let at: Date
        public let path: String
    }
    public struct Failure: Codable, Equatable, Sendable {
        public let at: Date
        public let message: String
    }
    public var lastSuccess: Success?
    public var lastFailure: Failure?
}
```

Written **before** anything could display it, which is what makes a quit-time failure visible
at all: the process is terminating and there is no UI left to show, so the record outlives it
and the next launch reports it. An unreadable or absent value reads as empty status, never
overwritten blindly — the posture `AppSettings` takes with a corrupt stored chord.

Three readers:

1. **`MenuBarModel`** — a warning row in the popover, and `MenuBarController` swaps the status
   item's symbol for a badged one. This is the reader that works with no window open, which is
   most of why it is the primary one.
2. **`MainWindowModel.autoExportProblem`** — its own property, rendered as its own banner.
   **Not folded into `lastError`.** A successful import clearing a standing backup failure is
   exactly the bug that forced `readError` and `writeError` apart in `MenuBarModel`, and the
   information at stake here is "you have no backup".
3. **The Data pane** — the full record, success or failure, with the path and the timestamp.

Cleared only by a successful export. The banner's dismiss button dismisses the banner for the
session; it does not clear the state, and the popover row and the Data pane keep saying so.

Rejected: **`UNUserNotificationCenter`**. It needs an authorization prompt, and a user who
denies it — or mutes Steno in Focus settings months later — restores exactly the silence §10.5
rules out. It would need the persisted channel underneath it anyway, at which point it is a
second mechanism that can only make the guarantee weaker.

Rejected: **a modal alert at next launch**. Impossible to miss, and an interruption on the
launch path, which §1.1 protects for capture.

## D-124 — Retention keeps the 14 newest by filename date, and the surplus goes to the Trash

`ExportFilename.forDate` is one file per local day and its own documentation defers collisions
to this task; the answer, matching `--output`'s, is overwrite. Fourteen files is therefore about
two weeks of daily history.

**Sorted by the date parsed out of the filename, never by modification time.** A cloud drive
rewrites mtime when it re-downloads a file, and an mtime-ordered sweep in a synced folder would
delete whichever files the sync engine happened to touch least recently. The filename date is
the durable key, and it is also the value the format actually carries — the same reasoning that
made sort keys serialized values in M2.5-01.

**Only exact matches are candidates.** `steno-export-YYYY-MM-DD.json` and nothing else, so a
manual export the user dropped into the same folder under any other name, and anything else
living there, is never a candidate for deletion.

**`FileManager.trashItem`, not `removeItem`.** This is a product whose event log is append-only
because permanent loss is the thing it refuses to risk; an over-eager retention bug that puts
files in the Trash is recoverable, and one that unlinks them is not. Trashing out of a synced
folder propagates a deletion to the cloud either way, so nothing is gained by unlinking.

**A failed trash is logged and nothing more.** The export succeeded; reporting a retention
hiccup through the failure channel would put a false alarm on the one channel that has to stay
trustworthy. The folder grows by one file and the next sweep tries again.

Rejected: **a configurable count**. A stepper in the Data pane, for a number nobody will change.

## D-125 — `StoreFileGuard` is extracted from the CLI and shared

`CLIRunner+Export` carries a `fileprivate isStoreFile` built over three PR-#31 review findings:
case-insensitive volumes, `fileResourceIdentifierKey` for files that exist, parent-symlink
resolution for files that do not, and `-wal` / `-shm` / `.steno-cli.lock` as protected
siblings. It exists because `--output ~/Library/Application Support/Steno/Steno.store`
atomically replaced the live database with JSON and said "Exported to …" while doing it.

Auto-export is a second writer that takes a destination from the user, writes there
unattended, and now also *deletes* files there. It needs the same guard, and a guard that lives
on one of two paths is a guard the next surface forgets. So it moves to
`StenoKit/Portability/StoreFileGuard.swift` as `internal` API with no behaviour change, the CLI
calls it, and auto-export calls it in two places:

- when a folder is **chosen**, so the mistake is refused while the user is looking at it;
- before **every write**, because the store's location is resolved from the open container's
  configurations and a folder validated months ago is not a promise about today.

The extraction is behaviour-preserving and the existing CLI tests are what prove it; they must
pass untouched.

## D-126 — Onboarding is one sheet, on the machinery that already exists

`ActiveSheet.autoExportOnboarding`, presented by `MainWindowModel` on first launch when
`AppSettings.hasSeenAutoExportOnboarding` is false and the store opened. Same presentation path
as the import preview, standup draft and note composer — no new window, no new scene, no
onboarding framework.

The sheet says what auto-export does, shows the folder it is already using, names Dropbox /
Google Drive / iCloud Drive as the folder worth choosing, and offers **Choose Folder…** and
**Done**. There is no enable checkbox, because it is already enabled; presenting one would
invite the user to answer a question §10.5 has already answered.

A store that failed to open shows no sheet and writes no flag, so onboarding appears on the
next healthy launch rather than being consumed by a broken one.

Rejected: **a reusable multi-step onboarding framework** with auto-export as step one. There is
no second step to validate the abstraction against, and M3-04 and M4-04 are Settings panes, not
onboarding steps.

## D-127 — The Data pane arrives carrying auto-export only

`SettingsPane` has held `// case data — M2.5: export as JSON, purge cached external data`
since M1-08. This task uncomments it: one enum case, one `title`, one `systemImage`, one arm in
`SettingsView`'s exhaustive switch, one new view file. That is the whole extension mechanism
M1-08 built, exercised for the first time.

The pane carries: the enable toggle, the folder with **Choose Folder…**, the two trigger
toggles, the last result (success with path and time, or the failure message), and **Export
now**. FR-6's "export all data as JSON" is already the File menu's Export item and is not
duplicated here. FR-6's "purge cached external data" is left unbuilt and the comment in the
enum is narrowed to say so — there is no cached external data until M4, and a button that
purges nothing is a button whose behaviour nobody can verify.

## Architecture

Everything decidable lives in `StenoKit`, because the test bundle is unhosted and links the
framework rather than the app (D-010). The app target's share is the wiring: a controller built
in `StenoApp.init`, a `Timer`, and one delegate method.

### `StenoKit/Portability/AutoExport/`

**`AutoExportSettings`** — not a new type. Six additions to `AppSettings`, which exists so that
§10.3's "secrets are never exported" audit has one place to look:

| Property | Type | Default when absent |
|---|---|---|
| `autoExportEnabled` | `Bool` | **`true`** |
| `autoExportOnQuit` | `Bool` | `true` |
| `autoExportDaily` | `Bool` | `true` |
| `autoExportFolder` | `URL` | `~/Steno Backups` |
| `autoExportStatus` | `AutoExportStatus` | empty |
| `hasSeenAutoExportOnboarding` | `Bool` | `false` |

The three `Bool`s default to `true`, which `UserDefaults.bool(forKey:)` cannot express — it
returns `false` for an absent key, which is the wrong answer for all three. Each reads
`object(forKey:) as? Bool ?? true`. This is small and it is exactly the kind of small thing
that turns "defaults ON" into "defaults OFF" on a fresh install, so it gets its own test.

**`AutoExportService`** — the write, and nothing else. Injected the way `BackupWriter` is
injected, so the headless bundle drives it entirely inside a temp directory:

```swift
@MainActor
public struct AutoExportService {
    public init(
        context: ModelContext,
        settings: AppSettings = AppSettings(),
        now: @escaping () -> Date = Date.init,
        write: @escaping (Data, URL) throws -> Void = { try $0.write(to: $1, options: .atomic) },
        trash: @escaping (URL) throws -> Void = { try FileManager.default.trashItem(at: $0, resultingItemURL: nil) },
        contents: @escaping (URL) throws -> [URL] = { try FileManager.default.contentsOfDirectory(at: $0, includingPropertiesForKeys: nil) }
    )

    @discardableResult
    public func run(trigger: AutoExportTrigger) -> AutoExportOutcome
}
```

`run` does not throw. Every failure it can have is one the user must be told about rather than
one a caller could sensibly handle, so it records the outcome in `AutoExportStatus`, logs it,
and returns it:

```swift
public enum AutoExportTrigger: String, Sendable { case quit, daily, manual }

public enum AutoExportOutcome: Equatable, Sendable {
    case written(URL)
    case skipped(AutoExportSkip)   // .disabled, .triggerOff, .notDue
    case failed(String)            // the user-facing sentence, already persisted
}
```

The order inside `run` is: gate on the settings → resolve and guard the folder → create it if
absent → encode → write atomically → record success → sweep retention. Encoding before any
mutation of state, and recording success only after the write returns, means a throw anywhere
leaves the previous success record intact and adds a failure record beside it. `manual` is the
Data pane's **Export now**, which bypasses the dueness check but not the folder guard.

Two failures, two sentences — the distinction `MainWindowModel.exportStore()` and
`CLIRunner.export` both already draw: `encode()` failing means the *store* could not be read,
`write` failing means the *file* could not be written, and one message for both sends someone
whose store is busy off to check their disk.

**`AutoExportDue`** — pure, no clock of its own:

```swift
public enum AutoExportDue {
    public static let interval: TimeInterval = 24 * 60 * 60
    public static func isDue(lastSuccess: Date?, now: Date) -> Bool
}
```

**`AutoExportRetention`** — pure, over filenames:

```swift
public enum AutoExportRetention {
    public static let keep = 14
    public static func prunable(from urls: [URL], keeping: Int = keep) -> [URL]
}
```

Names that do not match `steno-export-YYYY-MM-DD.json` are not returned. Matching names sort
by their date component, which is lexicographic and chronological at once because the format is
zero-padded ISO-8601; ties cannot occur, because the name *is* the day.

**`AutoExportController`** — the small amount of state that is not a pure function:

```swift
@MainActor
public final class AutoExportController {
    public init(service: AutoExportService, settings: AppSettings = AppSettings())
    public func launch()     // the at-launch daily check
    public func tick()       // the hourly daily check
    public func quit()       // applicationWillTerminate
}
```

No `Ticker` protocol and no timer inside it: `StenoApp` owns a `Timer.scheduledTimer` that
calls `tick()`, and the tests call `tick()` directly. An injected ticker would be a protocol,
a fake and a real implementation in exchange for testing `Timer` itself.

### `StenoKit/Portability/StoreFileGuard.swift`

The extraction described in D-125, plus one addition auto-export needs and the CLI did not: a
folder-level check, since `--output` names a file and this names a directory.

### The app target

```swift
// StenoApp.init, inside the existing `if case .success(let container)` arm
autoExport = AutoExportController(service: AutoExportService(context: container.mainContext))
autoExport?.launch()
```

plus a `Timer` retained beside it, and `AppDelegate.applicationWillTerminate` calling
`autoExport.quit()` — reached through the delegate because `NSApplicationDelegateAdaptor`
already owns that seam and `StenoApp` is a `struct` rebuilt by SwiftUI.

Nothing is built when the store failed to open. That is §13's degradation, and it is also the
only honest behaviour: there is nothing to export.

### Surfaces

`FilePanels` gains one method, `chooseExportFolder(startingAt:) -> URL?`, with
`UnavailableFilePanels` refusing loudly the way D-109 established and `AppKitFilePanels`
running an `NSOpenPanel` with `canChooseDirectories = true`. Both the onboarding sheet and the
Data pane choose folders through it, so neither reaches AppKit and both are testable.

The service posts `.stenoAutoExportDidChange` after every run that changes status.
`MenuBarModel`, `MainWindowModel` and the Data pane's model each observe it, in the shape
`.stenoDidWrite` already establishes — no surface holds a reference to another.

## Error handling

| Failure | What the user gets |
|---|---|
| Folder missing or deleted | Recreated silently if its parent exists; otherwise a failure record naming the path |
| Permissions revoked, disk full | Failure record with the underlying message, on all three surfaces |
| Folder is Steno's own store directory | Refused at choose time with a sentence; refused again at write time |
| Store unreadable | "Steno could not read its own store, so nothing was exported" — distinct from a write failure |
| Trash unavailable | Logged only; the export still succeeded |
| Store failed to open at launch | No controller, no exports, and the Data pane says why |
| App force-quit | No export, nothing lost; the daily trigger catches up |

Every message follows the existing convention that the sentence says what was *not* changed.

## Testing

Headless, no network, no window server (§9.4). Folder, clock, `write`, `trash` and `contents`
are all injected, so every test runs inside a temp directory.

**`AutoExportDefaultsTests`** — a fresh `UserDefaults` suite yields enabled, both triggers on,
`~/Steno Backups`, empty status, onboarding unseen. The `?? true` reads are the point; a
mutation to `defaults.bool(forKey:)` must turn this suite red.

**`AutoExportDueTests`** — a table: never exported · 23h59m · exactly 24h · 25h · a last
success dated in the future.

**`AutoExportServiceTests`** — the file it writes is accepted by `ImportReader.read`; it
round-trips through `StoreMerge` unchanged; `CredentialPatterns` finds nothing in it (§10.3
matters more on the unattended path, not less); a fresh store and a populated one both work;
`.quit` writes with no dueness check while `.daily` respects one; success and failure records
land in status and the previous success survives a later failure.

**`AutoExportRetentionTests`** — twenty dated files, six pruned, the right six. Foreign files
in the folder survive. **The mtimes are set to disagree with the filename dates**, so an
implementation that sorts by modification time fails rather than passing by coincidence — the
determinism lesson from M2.5-01, where running a thing twice proved nothing.

**`AutoExportFailureTests`** — an injected throwing `write` produces a failure record, leaves
`lastSuccess` untouched, and returns the user-facing sentence; a throwing `trash` leaves the
export successful.

**`StoreFileGuardTests`** — the existing CLI cases move across unchanged and must pass
untouched; new cases cover a folder equal to, inside, and symlinked to the store directory.

**`AutoExportLatencyTests`** — median of repeated `AutoExportService.run` calls over a
realistic store, against a stated budget, with the measurement taken on `run` itself.

Before the PR, mutate each new assertion and confirm the suite goes red: flip the `?? true`
defaults, sort retention by mtime, drop the folder guard, skip the status write on failure, and
neutralise the whole dueness guard rather than one clause of it.

## Manual verification (PR body)

Agents cannot see a window or click anything, so these are run by hand and recorded:

- First launch on a fresh defaults domain shows the onboarding sheet; **Done** leaves a file in
  `~/Steno Backups`.
- **Choose Folder…** into a Dropbox or iCloud Drive folder; quit and relaunch; a later export
  still lands there — the "persists across relaunch" criterion.
- Quit with ⌘Q: no perceptible delay, and the day's file is updated.
- Rename the target folder out from under the app, then quit: the next launch shows the failure
  on the menu bar icon, in the popover, in the main window banner, and in the Data pane.
- A successful export clears all four.

## Out of scope

- **Export and import mechanics** — M2.5-01 and M2.5-02 (task file).
- **Real-time sync.** Cancelled (D1, §14). Auto-export into a cloud folder is the substitute,
  and §10.5 is candid that it is not convergence: a machine must export before the other
  imports. Do not try to close that gap.
- **FR-6's cache purge** — no cached data exists until M4 (D-127).
- **A second onboarding step, or an onboarding framework** (D-126).
- **The closed-window File menu limitation**, narrowed and documented in M2.5-04. Auto-export
  does not depend on the File menu and does not change it.

## Note on Q(M2)

§12's remaining Q(M2) asks whether auto-export into a cloud folder is sufficient in daily
practice, or whether true concurrent multi-machine editing is needed sooner. This task makes
the question answerable for the first time. The PR reports the experience and nothing more —
if the answer turns out to be no, that reopens §14, which is a product decision and not an
implementation one.
